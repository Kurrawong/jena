What we're building

You call SQL directly

We index only what search needs. The index answers which holes; your warehouse answers what's in them.

  • Index carries the summary values — max per hole per analyte
  • Search, filter, facet and sort happen in Lucene
  • Result is a list of hole IRIs, plus counts
  • Your FE fetches the full assay table from SQL by those IRIs
The one-line version. The index is a search surface over your data, not a copy of it. Nothing you can read from Lucene is meant to be displayed as a value — it exists to narrow millions of holes down to the page in front of the user.
The problem

Why the assays don't belong in the graph

Loading the measurement data as RDF is the obvious move, and it is the wrong trade for this dataset.

Volume

The measurement table is an order of magnitude larger than the graph describing the same holes. Tens of millions of rows, hundreds of measured properties.

Authority

The warehouse is the source of truth. Copying it into RDF duplicates a volatile dataset for no modelling gain — and couples the graph's update cycle to a foreign release cadence.

Access pattern

Nobody traverses these values by SPARQL path. They're used as search machinery: range filters, range facets, sort. Then the real values come from SQL.

The alternative we rejected: a SQL property function

Query SQL live, at query time, from inside the search request. Perfectly fresh — and it can't participate in scoring, faceting, or sort pushdown, needs a live connection on the query path, and puts per-query load on the warehouse.

The choice is a data-cadence question. Batch-released data → index it. Continuously mutating data → push down to SQL.

What indexing buys

  • One query constrains across both sides: spatial + type + text from the graph, numeric ranges from the warehouse
  • Facet counts over millions of holes in milliseconds
  • Sort by a measured value, applied before paging
  • No connection to your database on the query path at all
How it fits together

The extract

What actually goes into the index

One narrow file: for each hole, one row per analyte, carrying the summary value. Your SQL computes it; the indexer only reads it.

Your side — one query 
SELECT  collar_id,
        analyte      AS property,
        MAX(value)   AS value,
        below_detection
FROM    assay_results
GROUP BY collar_id, analyte, below_detection
ORDER BY collar_id;   -- byte order

Why you compute the max

The indexer parses; it never computes. No units, no rescaling, no detection-limit arithmetic, no derived columns, no expression language.

That work already has a better home — your SELECT, versioned and tested where your analysts can see it. Admitting one expression into the config means admitting all of them, and the config becomes a program with no debugger.

The document model

One document per hole, with the measurements attached

Graph fields and external measurements sit side by side on the same document, so a single query can constrain across both.

Two field names, any number of analytes

The alternative was one field per analyte — Au_PPM, Cu_PPM, hundreds of them, sparse across every document.

The deciding argument is the public API surface, not size. Disk is cheap and recoverable; a query API with hundreds of field names in it is neither.

No RDF is invented. These external values never enter the graph. A "field" here is an internal index name, not a predicate — your ontology is untouched.
Configuration

The whole thing is declared, not coded

One block in the dataset config binds columns to index fields. No pipeline, no glue script, no transformation step.

# the two external fields — no sh:path,
# their values come from CSV columns
field:analyte
    idx:fieldType idx:KeywordField ;
    idx:facetable true ;
    idx:stored    true .   # short label, safe

field:analyteValue
    idx:fieldType idx:DoubleField ;
    idx:indexed   true ;   # range filters
    idx:facetable true ;   # range facets
    idx:sortable  true ;   # sort by value
    idx:stored    false .  # SQL owns the value
No external flag exists. A field is external because a column binds it — one source of truth, nothing that can contradict itself. 
:CollarShape
    sh:targetClass ex:Collar ;

    # graph-derived fields, exactly as before
    sh:property [ idx:field field:region   ; sh:path ex:region ] ;
    sh:property [ idx:field field:location ; sh:path geo:asWKT ] ;

    # one child document per CSV row
    idx:nested [
        idx:nestedName "measurement" ;
        idx:externalSource [
            idx:format        idx:CsvFile ;
            idx:location      "data/measurements.csv" ;
            idx:subjectColumn "collar_id" ;
            idx:subjectPrefix ".../gswa/collar/" ;

            idx:column [ idx:columnName "property"
                       ; idx:field field:analyte ] ;
            idx:column [ idx:columnName "value"
                       ; idx:field field:analyteValue ] ;
            idx:column [ idx:columnName "below_detection"
                       ; idx:field field:belowDetection ] ;
        ] ;
    ] .
Query capability

What the front end can ask for

Every filter below runs in one Lucene query, across graph fields and measurements together, and returns hole IRIs.

Correlated within one measurement

"Gold above 1 ppm, and not a detection-limit placeholder"

{"op":"and","args":[
  {"op":"=",  "args":[{"property":"…#analyte"},"Au"]},
  {"op":">=", "args":[{"property":"…#analyteValue"},1.0]},
  {"op":"=",  "args":[{"property":"…#belowDetection"},"f"]}
]}

All three conditions must hold on the same measurement record. Exact, no false positives.

Across both sides at once

"RC holes in the Pilbara, drilled since 2010, with Cu over 500 ppm"

Three graph fields and one measurement condition in a single query. The map extent, the facet selections and the geochemical thresholds are all one Lucene call.

  • Text search on hole name and prospect
  • Keyword filters on operator, region, drill type, status
  • Numeric ranges on year and depth
  • Spatial filter on the collar location
Entity-level conjunction

"Holes with some Au over 0.5 and some Cu over 100"

Two conditions on two different analytes are two separate measurements, so this means "this hole has both" — not "in the same sample".

Worth stating plainly to your users. If "the same interval" ever matters, the fix is a wider extract — extra columns, no code change. We can walk through that when it comes up.

Also available

OR, IN, BETWEEN, LIKE

  • OR across analytes — "Au over 1 or Cu over 500"
  • IN lists, BETWEEN ranges, wildcard text
  • Arbitrary nesting of AND/OR groups
  • Total hit count returned alongside the page, for pagination
Navigation

Facet counts and sort, computed inside the index

The two things a results page needs that a plain filter can't give you.

Facets — "how many holes are left if I click this?"

Ask for counts over any facetable field, under the current filter. One call, all dimensions.

// request
["…#region", "…#drillType", "…#analyte",
 {"field":"…#analyteValue",
  "ranges":[null,0.1,1,5,null]}]

// response rows
region     "Pilbara"      4 812
region     "Great Southern" 1 067
drillType  "RC"           3 991
analyte    "Au"           5 604
analyte    "Cu"           5 511
analyteValue  [1 – 5)       842

Both flat counts and numeric range bands, in the same request. Bucket boundaries are yours to choose per request.

Sort by one analyte's value

"Order these holes by their gold value, highest first" — where each hole has dozens of measurements and only one of them is gold.

{
  "field":    "…#analyteValue",
  "selector": {"field":"…#analyte", "eq":"Au"},
  "order":    "desc",
  "missing":  "last"
}
  • The selector picks which measurement supplies the sort key — it doesn't remove holes
  • Holes with no gold result keep their place, positioned by missing
  • Sorting happens before paging, so page 7 is still correct
Both of these are why the values are indexed at all. You can't compute a facet count or a global sort order from a page of results — they need every matching document, which is exactly what the index has and a per-page SQL call does not.

Snapshot

The filter itself

If a value moves 90 → 110 in the warehouse and the index hasn't been rebuilt, the hole is still filtered as 90. It would be missing from a "greater than 100" search until the next build.

So: rebuild cadence must match your release cadence. A batch-released extract fits this model exactly. A continuously mutating table does not, and should be pushed down to SQL at query time instead.

Nightly build — typical On data release — ideal Live streaming — not this mechanism
What we need from you to size this: how often the measurement extract is regenerated, and whether an index that trails it by one release cycle is acceptable to your users. That answer sets the build schedule and nothing else in the design changes.
Operational safety

The failure we designed hardest against

A build that "succeeds" and produces an index where nothing matches. It's the worst outcome available here, because it looks fine until a user complains.

How it happens

One wrong character in the IRI prefix, or an extract re-sorted numerically instead of by text, and every row silently fails to join. Rows read: 40 million. Holes matched: zero. Exit code: success.

How we stop it

  • Minimum match rate — declare that at least half the holes must match, and a build that doesn't fails rather than publishing
  • Sort order is verified, not trusted — a row out of order fails the build, one string comparison per row
  • Counters on every build — rows read, matched, unmatched, skipped, always logged

Rows augment; they never create

A measurement whose hole isn't in the graph is counted and dropped. External content decorates entities the graph already knows about — a bad extract can't invent or destroy documents.

A hole with no measurements is still indexed

It gets its graph fields and no children. Sparse coverage is normal and doesn't make holes disappear from search.

Bad rows drop whole

An empty or unparseable cell drops the entire row — never coerced to zero, never emitted half-populated. A half-child would match a filter on the analyte while contributing nothing to the range test.

One operational rule. Measurement children are populated by the bulk build only. An in-place graph edit to a hole of this shape is refused with a warning rather than silently rewriting the document without its measurements — Lucene has no partial document update, so the safe answer is to re-run the build.
Where it stands

Built, tested, and demonstrable now

Phase 1 is complete on the feature branch, with the real extract shape covered end to end.

Phase 1 — done

CSV / TSV ingest

  • Streaming merge-join on the hole IRI
  • IRI prefixing from a bare key
  • Sorted and unsorted input
  • Filters, facets, range facets, sort
  • Match-rate and sort-order guards
  • Glob input — meas-*.csv

54 new automated tests, including seven written against the exact shape of your extract — bare integer key, scientific notation, detection flag, mixed-width ids.

Phase 2 — designed

Straight from SQL

A JDBC source removes the export-a-file step entirely: the build connects to the warehouse, pushes the ORDER BY and column projection down into your database, and streams the result.

Also queued: pivoted/wide extracts, Parquet, and external sort for very large unsorted inputs.

Small piece of work — the source interface was built for exactly this.

Phase 3 — designed

Incremental updates

Rather than rebuilding everything, a delta file carrying only added and removed measurements, with the indexer rebuilding just the affected holes.

Deferred deliberately: for a batch-released extract, a full rebuild is correct, simpler, and fast enough.

Open question for you, and it's the one that isn't cheap to reverse later: what a document represents. One document per hole is comfortable at your scale. One document per sample would multiply the child count and hit a hard platform ceiling. We should confirm this against the real catalogue before loading at full volume — the mechanism is identical either way, only the arithmetic changes.
