# Demo: External Content Indexing

One Lucene document per drillhole collar, carrying **graph-derived fields and external
measurements side by side**, so a single query can constrain across both.

- **Collars** come from RDF: label, prospect, operator, region, drill type, status,
  depth, year, geometry.
- **Assays** come from a CSV that is never loaded into the graph. Each row becomes a
  nested child document inside the collar's Lucene block.
- The two meet on the **collar IRI**, at document-construction time.

Design note: [`docs/2026-07-27_external_content_indexing_design.md`](../../docs/2026-07-27_external_content_indexing_design.md).
Configuration reference: [`docs/03-configuration.md`](../../docs/03-configuration.md#external-content-csvtsv).

## The data

`data/measurements.csv` is a **real slice** of the GSWA downhole summary extract
(`dh_summary_measurements.csv`) — the first complete collar groups from the head of the
dump:

```
collar_id,property,value,below_detection
1000000,As,98.4000015258789,f
1000000,Au,8.900000102585182e-05,f
1000000,Cu,83.5,f
```

996 rows, 119 collars, 37 analytes, 78 of them below detection limit.

`data/collars.ttl` is **synthetic**, generated by `tools/make-collars.py`. The collar ids
are real; everything else about the collars is invented, because the real collar table is
not part of this repo. Regeneration is deterministic — each collar is seeded from its id.

Three things about this extract are not incidental:

| | |
|---|---|
| The join key is a **bare integer** | `idx:subjectPrefix` turns `1000000` into the collar IRI. Repeating a 50-character IRI across 29.7 M rows would be pure file bloat |
| Values arrive in **scientific notation** | `8.900000102585182e-05`. Trace assays span many orders of magnitude, and lexically that value sorts between `83.5` and `98.4` |
| Collar ids are **6 and 7 digits** | so lexical and numeric order disagree — see below |

## Sort order: the one thing to get right

The streaming merge consumes rows in **lexical** order. The dump is sorted that way
already:

```
lexical:  1175968  <  117597  <  1175971  <  117598      ← the dump's order
numeric:   117597  <  117598  <  1175968  <  1175971     ← what ORDER BY collar_id gives
```

Verified across all 29,707,585 rows of the full dump: no violations. So `idx:sorted true`
is safe as-is.

But re-exporting with `ORDER BY collar_id` on the integer column would produce the second
order, and the build would **reject it** with a message naming the offending pair — rather
than merging to a technically successful index with almost nothing in it. Check any new
extract before trusting it:

```bash
task check-sorted
```

To fix an out-of-order file, either re-sort it (`LC_ALL=C sort -t, -k1,1 -s`, keeping the
header aside) or set `idx:sorted false` and let the indexer buffer it in memory — fine for
a slice this size, untenable for the full 29.7 M rows.

## Quick start

```bash
# 1. Build the Fuseki server JAR (from the repo root, or: task build)
task build

# 2. Load the collars into TDB2 and bulk-index collars + measurements
task rebuild

# 3. Serve (port 3031, so it can run alongside the other demos on 3030)
task serve

# 4. In another terminal — the standalone page
task app          # http://localhost:8010/index.html

# …or just run the headline queries
task smoke
```

`task rebuild` prints the merge counters, which are the thing to read:

```
External source CSV data/measurements.csv [measurement]:
  996 rows read, 996 matched, 0 unmatched, 0 skipped; 119 of 119 entities matched (100.0%)
```

## Why bulk indexing, and not just loading the data

A profile with an `idx:externalSource` is **rebuild-only**. Lucene has no partial document
update and a block join must be written atomically, so an entity's complete child set has
to be in hand before anything is written. A live graph change cannot re-derive the
external children, so `ShaclTextDocProducer` refuses to rebuild such a document and says
so — rather than quietly writing one that has lost them.

Hence the two-step: `tdb2.tdbloader` (which bypasses the change listener) then
`shacltextindexer`.

This is also why `config.ttl` sets **`text:taxonomyDirectory`**. Hierarchical facet
ordinals live in a taxonomy index; left unconfigured it is in-memory, which is invisible
when indexing and querying share a JVM and fatal when they do not — the bulk build would
write the ordinals, exit, and the server would start on an empty taxonomy and report no
hierarchical facet counts at all, silently.

## What the demo shows

| | Query |
|---|---|
| Filter on external values | collars with any Au assay |
| **Same-child correlation** | `analyte = Au` **and** `value > 0.05` **and** `belowDetection = f` — one measurement must satisfy all three, not three different ones on the same hole |
| Graph **and** external together | Diamond holes with Cu over 50 ppm |
| **Sort by a not-stored value** | top collars by gold grade, via the nested sort selector — the key comes from the child whose analyte matches |
| Facets across the boundary | region counts (graph) restricted by an Au filter (external) |
| Property as a facet dimension | the analyte facet, free under the nested model |

The page never displays a grade. `field:analyteValue` is `idx:stored false`: the index
holds points and docvalues, so values can be filtered, faceted and sorted on, but never
returned. The assay database stays the source of truth and the index cannot serve a stale
number. Note this removes *display* staleness only — the filter is still a snapshot, so
rebuild cadence must match the source's release cadence.

## Full scale

The slice above is for reading. To index the **whole dump**:

```bash
task link-full          # symlink the dump (SRC=... to point elsewhere)
task check-sorted-full  # optional; a few minutes over 29.7 M rows
task reindex-full       # collars -> TDB2 -> Lucene
task serve-full         # port 3032
task smoke-full
```

The page points at whichever index you give it:

```
http://localhost:8010/index.html              # the 996-row slice (:3031)
http://localhost:8010/index.html?port=3032    # the full 29.7 M-row index
```

Everything lives in its own directories — `DB-full/`, `Lucene-full/`,
`Taxonomy-full/` — so a full build never disturbs the small demo, and the two can
be served side by side.

### Measured, not projected

| | |
|---|---|
| Collars | 2,470,212 |
| Measurement rows | 29,707,584 |
| Rows per collar | ~12 |
| Lucene documents | ~32.2 M (29.7 M children + 2.47 M parents) |
| `IndexWriter.MAX_DOCS` ceiling | ~2.15 billion |
| **Rows matched** | **29,707,584 — 0 unmatched, 0 skipped** |
| **Collars matched** | **2,470,212 of 2,470,212 (100%)** |
| TDB2 load | 27.2 M triples in 2m07 (216 K triples/sec) |
| Index build | 6m08 (6,730 entities/sec) |

The ceiling row is the point. Child-document count is `entities × populated
properties`, and it is the constraint that decides whether the nested EAV model is
viable at all — see [The granularity constraint](../../docs/2026-07-27_external_content_indexing_design.md#the-granularity-constraint).
At this grain the model has roughly **two orders of magnitude of headroom**.

### What it costs on disk

`task measure-split` builds the same collars a second time without the `idx:nested`
block and differences the two indexes, which attributes bytes to origin exactly:

| | |
|---|---|
| Total Lucene index | **1,338 MB** |
| — graph-derived (parents only) | 257 MB — 109 bytes/collar |
| — external content | **1,082 MB — 38.2 bytes per child** |
| Facet taxonomy | 104 KB |
| TDB2 (the synthetic graph) | 4.3 GB |

Where the external bytes go: docvalues (sort keys, facet values) and BKD point trees
(range filters), with almost nothing in stored fields — `analyteValue` is
`idx:stored false`, so the value is searchable but never returned. The term
dictionary is 13 MB for 29.7 M measurements, because the nested model has ~37
distinct analyte terms regardless of row count. A flat model would have put a field
per analyte into the schema and the API.

Note the whole search index is smaller than the TDB2 store holding only ~11 triples
per collar. Materialising these measurements as triples would have cost far more
than indexing them does.

Caveat: at measurement time the full index still held ~662 MB in unmerged compound
segments against the twin's ~3 MB, so a `forceMerge` would likely shift the split
somewhat toward the external side. Good enough for capacity planning, not a
precision figure.

### A data-quality note: sentinel values

Sorting the full index by gold grade returns collars whose Au value is `999909`.
That is not a grade — it is a placeholder in the source data, and 999909 sorts above
every real assay.

The indexer will not fix this, by design: it parses, it never computes, so there is
no config in which `999909` becomes "no data". A sentinel either gets filtered out of
the extract upstream, or every "highest grade" query in the deployment leads with it.
This is exactly the boundary the design draws in
[Why no transformation language](../../docs/2026-07-27_external_content_indexing_design.md#discussion)
— worth resolving in the `SELECT` that produces the CSV before this goes anywhere
near users.

Two things make the build practical at this size:

- **`idx:sorted true`** keeps the join streaming — O(N + M), constant memory,
  sequential I/O. Buffering 29.7 M rows instead is not an option.
- **Heap.** Discovery materialises every work item before sorting them by entity IRI,
  which the merge requires, so the tasks pass `-Xmx8g`. That is a real characteristic
  of the current implementation, not a tuning preference.

`data/collars-full.ttl` (~970 MB) and the symlink are generated and git-ignored; the
dump itself stays outside the repo.

## Regenerating from a different slice

```bash
task extract ROWS=5000                     # from the default dump path
task extract ROWS=5000 SRC=/path/to/dump.csv
task check-sorted
task rebuild
```

`tools/extract-measurements.py` keeps only **complete** collar groups — a truncated
trailing group would look like a collar that genuinely has fewer analytes than it does.

## Files

```
config.ttl                     Fuseki + SHACL index config (the idx:externalSource block)
data/measurements.csv          real GSWA slice — the external source
data/collars.ttl               synthetic collars — the graph side (generated)
app/index.html                 standalone demo page, no build step
tools/extract-measurements.py  slice the full dump, keeping whole collar groups
tools/make-collars.py          synthesise collars for the ids in a slice
tools/check-sorted.py          verify lexical ordering before trusting idx:sorted true
tools/smoke.sh                 the headline queries, as curl
```
